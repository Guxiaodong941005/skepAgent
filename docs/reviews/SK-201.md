## Findings

### Blocking

### Non-blocking

1. **(Architect) A failed top-of-stack verification has no protocol path.** §9.8 says the owner
   emits "`work.failed` on the top item if the combined result fails". By then, though, the task
   is `delivered` and the top item has no lease. `work.failed` is only allowed in
   `executing`/`interrupting` and is fenced, so it can't be accepted. `task.verified{passed:
   false}` is recorded, as tested in "keeps a failed verification result…", but nothing changes,
   and `item.merged` can still take the task to `done`. Proposed resolution: `task.verified{passed:
   false}` ⇒ `escalated` (reason `verification_failed`). Record it as a decision and assign it to
   SK-606 or a small reducer follow-up.
2. **(Architect) `budget_exceeded` during `interrupting` doesn't escalate.** Per the brief, a
   failure in `interrupting` only settles the barrier. The test "settles an interrupting budget
   failure using the barrier's replan budget" pins that behaviour. Invocation and wall budgets are
   task-level (D8), so arguably exhaustion should escalate even mid-barrier. This is acceptable for
   the MVP (the replan goes back to the owner, then to the human), but say so explicitly in §5.5.
3. **(SK-208 / plan.ts) Activation can leave a task with nothing to do.** If a replan carries over
   *every* item as `delivered`/`merged` (D7), `activatePlan` sets `executing` and no
   `work.delivered` will ever arrive to move the task to `delivered`/`done`. This is outside SK-201's
   files. `activatePlan` should finish with the same "all delivered ⇒ `delivered`; all merged ⇒
   `done`" check. SK-208 owns `plan.ts` in Wave 2, so it can fold this in.
4. **`max_parallel` counts interrupted leases.** The count uses `item.lease?.holder === actor`.
   Under §5.5 a checkpointed item keeps its (interrupted) lease object until the next plan
   activation. So an agent whose item is parked in a `replanning` or `escalated` task, possibly for
   hours while the human decides, can't claim in another task when `max_parallel_items` is 1.
   Counting only items with `status === "leased"` (or `lease.interrupt === null || item not
   checkpointed`) matches "active leases". Coordinate with SK-202, which owns the checkpoint
   transition.
5. `handleLeaseClaimed` re-checks `plan_hash` against the **active** plan after `checkPre` has
   compared it with the **current** plan. That's good defence in depth, and it's tested ("checks the
   active plan hash even when current-plan preconditions match"). It's worth a one-line comment
   that the two can differ only through an internal inconsistency.
6. `barrier.ts` has no doc comments, while the other handler files cite §5.5. Add one sentence on
   what "settled" means (checkpointed, or lease cleared by release/revoke/failure) and that SK-202
   depends on it.
