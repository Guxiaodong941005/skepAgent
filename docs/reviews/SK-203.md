# Review — SK-203 Git log reader → `LogEntry[]` (incremental)

* Branch: `task/SK-203-git-log-reader` (1 commit: `e4d628e`) · Implementer: codex (committed by the
  orchestrator) · Reviewer: architect
* Date: 2026-10-06

## Verdict: **FAIL** (two availability bugs reachable by an unsigned commit; otherwise strong)

The implementation is careful and very well tested. Highlights:
* the first-parent snapshot is taken once;
* `from` is checked with both `merge-base --is-ancestor` and membership in the chain, and `seq`
  is cross-checked;
* metadata and verification argv are batched under 64 KiB;
* repo-local config is neutralised;
* lossy UTF-8 decoding is detected by re-hashing the blob against its object ID.

All six numbered acceptance criteria have meaningful tests, and they pass.

It fails because of two **real bugs**. In both, a single commit that the reducer must treat as an
invalid no-op instead makes `readLog` throw for the whole log, on every call, on every device.
Anyone with write access to the blackboard remote can create such a commit, even without a
signing key: a leaked deploy key, the host's web UI, or a buggy client. That is exactly the
"forged coordination records" threat in PRD §11.1. PRD §8.2 rule 6 requires such commits to be
"skipped as no-ops", and the `LogEntry` contract (`src/core/log.ts`) represents them as `null`
content so that the reducer records `unreadable_event` / `bad_event_path`. Because the daemon can
no longer sync past that commit, the whole coordination protocol halts until someone rewrites the
blackboard's history by hand.

Finding B1 also contradicts the brief's algorithm step 4 ("size > `MAX_EVENT_BYTES` ⇒ `null`
without reading more than `MAX_EVENT_BYTES + 1` bytes into a string"). A code comment acknowledges
that the cap isn't enforced.

## Findings

### Blocking

**B1. A large blob under `events/` makes the log unreadable (no size cap before reading).**
`readAdded` requests every added `events/*` blob through `cat-file --batch`, and `NodeGitRunner`
buffers the full stdout as a string, with `maxBuffer` set to 16 MiB. The size check happens only
*after* the whole blob has been read. Reproduced on the branch with an **unsigned** commit adding a
20 MiB `events/big.json`:

```text
readLog(...) ⇒ LogReadError: Cannot read blackboard log in …: git --no-replace-objects cat-file
               --batch=skep-… -z failed (-1): stdout maxBuffer length exceeded
```

Below the 16 MiB limit, the reader still holds up to roughly 16 MiB per oversized file (several of
them in one batch can add up to more) and hashes it, all for content that ends up as `null`.

Fix (keeps the process bound in AC 5): first run `git cat-file --batch-check='%(objectname)
%(objecttype) %(objectsize)' -z` over the same requests to get sizes. Then send only blobs with
`size ≤ MAX_EVENT_BYTES` (and `type == blob`) to `--batch`. Everything else is `null` without being
read. Add a test with a blob above the runner's `maxBuffer`, for example 17 MiB, which is cheap to
create once in a temp repo.

**B2. A non-UTF-8 path under `events/` makes the log unreadable.** `diff-tree -z` emits raw path
bytes, and `NodeGitRunner` decodes them as UTF-8, so `\xff` becomes U+FFFD. The reader then asks
`cat-file` for `<sha>:events/�.json`, which doesn't exist. The `missing` record (which has
no marker) desynchronises the frame parser. Reproduced with an unsigned commit adding
`events/\xff.json`:

```text
readLog(...) ⇒ LogReadError: git cat-file returned a truncated blob for skep.json
```

The reducer would reject that path anyway (`bad_event_path`, since the event-path regex is ASCII),
so the reader must not throw. Fix, in either order:
* Only request blobs whose path matches the protocol shape (`parseEventPath(path) !== null`, or
  at least ASCII-only). Any other `A` path keeps no `added` entry, so `structural` yields
  `bad_event_path`.
* Parse `missing` / `ambiguous` batch records explicitly (`<object> missing` has no custom
  format) and map them to `null`, instead of treating them as a framing error.

Add a test with a non-UTF-8 path under `events/`, and one where the requested object is missing.

### Non-blocking

1. **`signatureGit` depends on the internals of `verifyCommits`.** The wrapper assumes the shas are
   the last `shas.length` arguments followed by `--`, in the same order. That holds today because
   `verifyCommits` de-duplicates with an insertion-ordered `Set` and appends `--`. Any change in
   `verify.ts` breaks it silently, or throws on a mangled prefix. Prefer calling `verifyCommits`
   once per sha batch (`batches([], shas)`) and merging the records. It costs the same number of
   processes and needs no argv surgery.
2. **Commits with a non-UTF-8 message or author** are handled correctly, because only `%H`/`%P`
   are read. A comment saying the format must stay hex-only would help keep it that way.
3. The custom `--batch` marker derives from a hash of the request list, so a blob can't
   practically contain the next frame's marker. The reasoning is sound but subtle; one sentence of
   comment on why a predictable marker is still safe would help reviewers.
4. Per-commit `diff-tree` is allowed by the brief. For long histories (SK-302 full replays in
   `skep doctor`), `git log --first-parent -m --name-status -z --format=…` or a
   `diff-tree --stdin` process could do it in one process later.

## Suggested follow-ups

* Fix B1 and B2 on this branch with the tests described above, then re-review. Both are small,
  local changes in `readAdded` and its request filter. SK-301/SK-302 build on this reader, so it
  should land fixed.
* SK-404 `forged-commits` scenario: include an unsigned oversized event and a non-UTF-8 event path,
  so the simulator keeps guarding this class of bug.
* SK-302: when `readLog` throws `LogReadError` for anything other than a history rewrite, raise an
  alarm and keep serving the last good state rather than crash-looping.

### Remaining notes (no action required)

* AC 5 now counts **two** `cat-file` calls for 50 small commits (size check + one content batch;
  the test asserts 55 total calls). This is the deliberate cost of the B1 fix, which the first
  review proposed. Large logs with many near-limit or invalid blobs add one content process per
  8 MiB of worst-case output, which is still bounded and independent of the number of oversized
  files.
* Valid-UTF-8 non-ASCII paths under `events/` are also no longer read. That's correct: the
  protocol's event path is ASCII-only, so the reducer rejects them as `bad_event_path` either way.
