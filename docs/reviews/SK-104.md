## Findings

### Blocking

None.

### Non-blocking

1. **`skepHome(env)` requires its argument.** The brief specified `skepHome(env?: NodeJS.ProcessEnv)`.
   Making it required is arguably safer (no hidden `process.env` reads, which a test asserts). Later
   tasks (SK-206, SK-607, the daemon) must pass `process.env` explicitly. Keep it this way, but note
   the change in ARCHITECTURE/DEV-PLAN when SK-206 lands.
2. **`runCli` mutates the caller's context.** It reassigns `ctx.output`, and the `preAction` hook
   replaces `ctx.env` and sets `ctx.paths`. That works for one process and one invocation. If tests
   or the IPC layer ever reuse a context, they could observe a stale `--home`. Consider
   `runCli` building an internal copy (`{ ...ctx }`) per invocation.
3. **The global `--version` long flag is dropped in favour of `-V`.** This deliberately avoids
   shadowing `plan show --version <n>`, and the code comment explains why. It's a sensible change,
   but `skep --version` now fails with "unknown option". Mention it in the CLI help/README, or
   rename the plan option to `--plan-version` in SK-604.
4. `task new --repo <name>` takes any string. Allowlist validation belongs to SK-603/SK-206, which is
   fine for a skeleton.
5. `src/bin/skep.ts` creates a context whose `output()` throws until `runCli` rebinds it. That's
   correct today, but fragile. It would be cleaner to let `runCli` construct the output itself and
   have `CliContext.output` be optional.

## Suggested follow-ups

* SK-603/604: decide between `--version` and `--plan-version`. Copy the context per invocation.
* SK-206/SK-607: call `skepHome(process.env)` explicitly; validate `--repo` against the device
  allowlist.
