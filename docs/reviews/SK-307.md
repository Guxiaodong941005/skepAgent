## Verdict: **PASS_WITH_NOTES**

`runStructured` follows ARCHITECTURE §9.3 exactly:

1. Derive the **original** JSON Schema from Zod and pass the adapter a *copy* (which the adapter may
   transform for its provider, as SK-207's `toCodexOutputSchema` does).
2. Classify process outcomes before touching the output, so a process failure never consumes the

## Implementer contract note: crashes as `completed` + non-zero exit

`AdapterResult.outcome` has no `crash` value, so a crashed CLI is `outcome: "completed"` with
`exitCode ≠ 0`, and `runStructured` maps that to `error: "crash"` without a repair.
**Judgement: acceptable, no contract change.** The adapter reports what the OS reported (exit
code), and classification is the runner's job (§9.3). The mapping is explicit and tested.
SK-504 maps `error: "crash"` ⇒ `work.failed{class: "crash"}`. A dedicated outcome would need a
change to the frozen contract for no behavioural gain. One caveat: a CLI that exits non-zero
*after* writing a valid final message is also classified as a crash. That is the conservative
choice, and the daemon must not treat a non-zero exit as success.

## Findings

### Blocking

None.

### Non-blocking

1. **A stray unmatched `{` before the JSON defeats extraction.** The scan only parses when the
   container stack returns to empty. With prose like `Using {x and then {"summary": …}`, the
   earlier `{` is never closed, so the real object is never parsed ⇒ `null` ⇒ an unnecessary
   repair. Add a fallback: if the forward scan finds nothing, try `JSON.parse` on the substrings
   from each `{` (right to left) up to the last balanced `}`. Add a test.
2. **Round-trip test with the real provider transform.** SK-207 dropped its own normalizer, and
   with it the tests that ran `toCodexOutputSchema` ⇒ provider-shaped value (all properties present,
   optionals `null`) ⇒ normalization ⇒ original Zod. Add one such test per model-facing schema
   (Plan, Review, WorkReport) to `structured.test.ts`, importing `toCodexOutputSchema` from
   `codex.ts`, now that both are on `main`.
3. **The schema appears twice in `outputSchema: "off"` mode.** Prompt builders already embed an
   "Output JSON Schema" section (`prompts.ts`), and SK-207's adapter appends the schema again in
   `"off"` mode. Remove one of them in a follow-up; preferably the adapter stops appending, since
   prompts own the text.
4. `extractJson` ignores top-level arrays by design (the schemas are objects). That is fine;
   document it in the doc comment.
