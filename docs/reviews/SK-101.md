# Review — SK-101 Reducer core: replay, structural rules, authz, preconditions, task & plan handlers

## Verdict: **FAIL** (one real bug; otherwise high quality)

The implementation is careful, pure and very well tested: 178 focused tests, every `InvalidReason`
exercised, deep-freeze purity tests, and incremental == full replay. All seven numbered acceptance
criteria are met. The verdict is `FAIL` because of one **real liveness bug** in the task/plan
handlers: once a task escalates on the review-round budget, a `human.decided` of `replan` or
`reassign_owner` cannot get it moving again. Every new proposal immediately re-escalates, plan
approval is impossible, and the only exit is cancellation (Finding B1).

The architecture text doesn't say explicitly that the counter must be reset, so part of the cause
is the spec. Still, ARCHITECTURE §5.5 clearly intends `human.decided{replan}` to return the task
to a workable `planning` state. The fix is a few lines plus tests.

## Findings

### Blocking

**B1. A review-round escalation deadlocks the task.** `review_rounds` is never reset or
re-granted, and `enforceReviewBudget` runs on every `plan.proposed`/`plan.rejected`. I reproduced
it against the branch with `LogBuilder` (default budget `review_rounds: 2`):

```text
v1,v2,v3 proposed+rejected      → status escalated, review_rounds 3
human.decided{replan}           → planning (review_rounds still 3)
plan.proposed v4 (owner)        → accepted, but status immediately escalated again
plan.approved v4 (human)        → rejected: bad_task_state   (status is escalated)
human.decided{resume_with_plan} → rejected: bad_decision     (no active plan yet)
```

`reassign_owner` behaves the same way. Only `task.cancelled` / `human.decided{cancel}` escapes.

Suggested fix (in `handlers/task.ts`; the owner of SK-101 should apply it):
* For `human.decided` with `replan` or `reassign_owner`, reset `review_rounds = 0`. The human has
  explicitly granted a fresh review budget. Also clear `barrier`, as ARCHITECTURE §5.5 says
  ("replan ⇒ planning; barrier cleared").
* Add tests: after a review-round escalation, `human.decided{replan}` followed by `plan.proposed`
  ⇒ `awaiting_approval`, then `plan.approved` ⇒ `executing`; and the same for `reassign_owner`
  with the new owner proposing.
* I'll record the rule in ARCHITECTURE §5.5 (budgets paragraph) as decision D12 when merging.
  `replan_count` deliberately stays as it is (the human is consulted on every further replan),
  while `review_rounds` resets.

### Non-blocking

1. **`plan.mode` must equal `task.mode`** (`invalid_plan` otherwise). This is stricter than PRD
   §9.1 ("a plan that the human approves with multiple items/devices switches to team mode"). With
   this rule, a default-solo task can never become team mode unless it was created with `--team`.
   The ARCHITECTURE table is ambiguous here, so I'm not blocking on it. Proposed resolution
   (architect, before SK-601): let the **plan's** mode decide routing and reviewers, and update
   `task.mode` on activation. Track as a follow-up.
2. **Two clones per entry.** `applyEntry` always does `structuredClone(state)` for `next`, and a
   second clone for the draft when an event reaches a handler. That's O(state) twice per commit,
   which is fine at MVP scale, but it grows with `outcomes`. The draft could be the single clone,
   with `next` derived from it on rejection (re-clone only then).
3. `handleAgentRegistered` re-checks the device (`unauthorized`), which `authorize` already
   guarantees. Harmless.
4. `activatePlan` throws `RangeError` on internal inconsistencies, such as a missing version or a
   `stack_order` entry without a definition. Schema validation makes these unreachable from a log,
   so throwing is acceptable. A comment saying they are unreachable by construction would help.
5. `human.decided{replan}` leaves `task.barrier` set. Because `checkpoint.recorded` and
   `replan.requested` aren't allowed in `planning` this has no effect yet, but SK-202 will rely on
   the barrier lifecycle, so clear it here (included in the B1 fix).
