## Verdict: **PASS_WITH_NOTES**

The writer and reader implement ARCHITECTURE §8 faithfully:

* **Writer:** one signed orphan commit per beat, built with plumbing (`hash-object` → `mktree` →
  `writeSignedCommit`), so `main`, the index and the worktree are never touched. Pushes use
  `--force-with-lease=<ref>:<last_oid>`. The duplicate-daemon alarm separates a real rival writer
  from a lost acknowledgement or a plain transport failure.
* **Reader:** verifies against the local trust root only, requires principal `daemon:<device of
  agent>` matching the registry, and rejects parents, extra tree entries, oversize content,
  invalid UTF-8 and schema violations, all per ref without failing the whole read.
* **Liveness tracker:** observer-relative on the injected monotonic clock, ignores `sent_at`,
  handles restart, and supports suspend reset.

The tests use real `git`/`ssh-keygen` in temp repos and are thorough. The notes concern the
"duplicate boot_id" signal on the observer side and the meaning of `unknown`.

## Findings

### Blocking

None.

### Non-blocking

1. **Observer-side duplicate detection.** §8.1 says the duplicate-daemon alarm is "also raised when
   two `boot_id`s are seen for one agent". The tracker resets on any new boot id (a legitimate
   restart), so a flip-flop A→B→A is never reported. Suggested rule: keep the last *two* boot ids
   per agent and raise an alarm (for example `classify(...).duplicate = true`, or a separate
   `alarms()` list) when a boot id that was already superseded re-appears. A restart never brings
   back an older boot id. Add it in a small follow-up here or in SK-601 when wiring alarms.
2. **The active-interval gap is reported as `unknown`.** For a lease holder (60 s cadence), ages
   between 180 s (3 × interval) and 300 s (`staleMs`) classify as `unknown`, the same label used
   for "fewer than two observations". The comment documents this and it follows §8.2 literally,
   but `skep status` (SK-604) should be able to distinguish it. Either add a `late` class or expose
   `observations` so the renderer can say "late" rather than "unknown". This is an architect
   decision; it affects only display, not protocol.
3. The cadence is inferred from `hb.epoch !== null` (holding a lease ⇒ 60 s, else 300 s), because
   `skep.hb/v1` has no interval field. That is correct for the MVP. If cadences ever become
   configurable, add an `interval_s` field in `skep.hb/v2` (§4.4) instead of inferring it.
4. The first beat after boot adopts whatever OID is on the remote (`ls-remote`). If a duplicate
   daemon is live at that moment, this boot overwrites it once, and the *other* daemon raises the
   alarm on its next beat. That is acceptable (the alarm still fires) and is documented in the code.
5. `readHeartbeats` runs one `verifyCommits` plus a few `cat-file` calls per agent ref. That is fine
   for the MVP (≤ a handful of agents); batching the verification like the log reader would be an
   easy later optimisation.
