## Implementer notes: judgement

* **Reassignment in `sleep-wake-revoke` goes through a human-approved replan.** **Correct for the
  MVP.** §6.1/§5.5 only let the plan's assignee claim, and there is no "reassign item" event; the
  only protocol path to move W1 to vps is `lease.revoked` ⇒ `replan.requested` (human, no evidence
  needed; nothing leased ⇒ immediately `replanning`) ⇒ plan v2 ⇒ approve. The item's epoch counter
  survives activation (§5.5), so the re-claim is epoch 2, which is exactly what fencing needs. PRD
  S5's wording ("re-leased to `vps.coding`") implies a lighter path. Record that as a known MVP
  limitation (V1: role-based claims). It is not a defect.
* **Shared scenario helpers live in `claim-race.ts`.** Acceptable, but a dedicated
  `scenarios/common.ts` would be clearer, since every scenario imports `TASK`, `ITEM`,
  `prepareTask`, `pushCode`, `deliveryDuties` and so on from `claim-race`. This is a cosmetic
  follow-up.

## Findings

### Blocking

### Non-blocking

1. **Test runtime needs tiering.** The 7 × 50-seed sweep makes `npm test` take ~5 min of wall time
   (it was ~30 s before), which slows every task's inner loop and every review. **Recommendation
   (follow-up):** read the seed count from `SKEP_SIM_SEEDS` (ARCHITECTURE §14 already names it)
   with a **default of 3 seeds** per scenario in `npm test`. Run the full 50-seed sweep (the
   acceptance bar) in an opt-in `npm run test:sim-full` / CI job, and before releases (SK-610
   checklist item 2). Keep the per-scenario seed-42 outcome tests in the default run.
2. **Duplicate code-host fake.** `claim-race.ts` implements its own `ScriptedCode` instead of
   SK-503's `FakeCodeHost` (on `main` before this branch). Switch to `FakeCodeHost`, adding a
   `pullRequests()` listing for invariant 5, so the sim exercises the same fake that SK-504/SK-606
   tests will use. The SK-503 review's "one PR per head in any state" note then applies to both.
3. The outcome test's `switch` on scenario name is long; moving each scenario's expectations next
   to the scenario (e.g. an `expect(world)` hook on `Scenario`) would scale better as SK-505/SK-605
   add scenarios. This is optional.
