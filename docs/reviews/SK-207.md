## Verdict: **FAIL**

**The adapter cannot produce a work report against the real CLI, which is the purpose of the
spike.** It passes the raw `z.toJSONSchema(...)` output to `--output-schema`, and the provider's
strict structured-output mode rejects that schema (finding B1). The orchestrator reproduced this
outside the sandbox with `codex-cli 0.160.0`. The spike report's conclusion ("Codex exposes every
required interface flag, so there is no demonstrated reason to select a fallback") is therefore
not supported. Everything else is solid and should be kept. The process handling, JSONL/usage
parsing, permission-prompt detection, timeout and abort via the injected ladder, the D19-compliant
environment handling and the report's structure are good work. The fix is bounded (see
"Required changes").

## Findings

### Blocking

**B1. The raw Zod JSON Schema is not accepted by the provider's strict structured-output mode.**
`invoke()` writes `JSON.stringify(inv.outputSchema)` unchanged to `schema.json`. This is not
specific to one test. All three model-facing schemas, run through `z.toJSONSchema`, contain
constructs outside the strict subset. The reviewer checked their keyword sets:

* work report: 3 optional properties; `oneOf`, `prefixItems`, `exclusiveMinimum`, `pattern`,
  `minLength`/`maxLength`, `minItems`/`maxItems`, `const`, `$schema`
* plan: 2 optional properties (`details`, `requires`); the same keyword families
* review: 4 optional properties; the same keyword families plus `oneOf` in the evidence unions

`oneOf` is rejected outright. Strict mode also requires every property to be listed in `required`
(optional fields must become required + nullable) and does not accept several validation keywords.
As implemented, every `work`, `plan` and `review` invocation fails with exit 1 before the model
runs, which would surface as `invalid_output`/`crash` on every attempt.

### Non-blocking

1. `probe()` spawns with `env: {}`. Whether `codex` is then found on `PATH` depends on the runtime's
   spawn semantics (an empty env gives no `PATH`). Pass a minimal `PATH` (from the caller's
   sanitized env) or require `codexPath` to be absolute.
2. `probe().ok` compares with the hard-coded `PINNED_CODEX_VERSION`. ARCHITECTURE §9.2 says the
   pin lives in AGENT.md (`cli_version`). Keep the constant as the *tested* version for the report,
   but let the daemon compare `probe().version` with AGENT.md, so a deliberate upgrade does not
   need a code change.
3. A rejected schema is indistinguishable from a model failure in `AdapterResult` (exit 1, no last
   message). Detect the provider's `invalid_json_schema` error in the captured log and throw
   `CodexAdapterError` (a configuration error, alarm), so it is never retried as `invalid_output`.
4. Record the orchestrator's real-CLI SIGINT result in the report (criterion 3).

## Required changes (decision per ARCHITECTURE §9)

ARCHITECTURE §9.1–§9.3 assigns the roles. The **adapter** owns everything CLI- and
provider-specific. The structured runner (SK-307) owns validation with the **strict Zod schema**
and the single repair. The provider-side schema is therefore only a *generation constraint*; Zod
stays the authority. The right fix is:

1. **Provider-compatible schema transform in the adapter** (`codex.ts`, e.g. an exported pure
   `toCodexOutputSchema(jsonSchema)` with unit tests):
   * `oneOf` ⇒ `anyOf`; `const` ⇒ single-value `enum` if `const` is not accepted.
   * Every object: `additionalProperties: false`, **all properties in `required`**; properties
     that were optional become `anyOf: [<schema>, {"type": "null"}]`.
   * `prefixItems` tuples ⇒ a plain `items` array of the union of the element types.
   * Drop `$schema` and any keyword the provider's strict mode rejects (verify `pattern`,
     `minLength`/`maxLength`, `minItems`/`maxItems`, `minimum`/`exclusiveMinimum`, `format`
     against the real CLI and keep the ones it accepts).
   * Being lossy here is acceptable because Zod re-validates everything afterwards (including
     `superRefine` rules such as the linear stack, which JSON Schema cannot express anyway).
2. **Null normalization before Zod validation (SK-307, `structured.ts`):** before `schema.parse`,
   remove `null` values for properties that the *original* JSON Schema did not list as required.
   This is a generic walk over the original `outputSchema` and the value, so optional fields
   decode exactly as Zod expects. Add this to SK-307's brief (it is in Batch B and has not
   started).
3. **Opt-in real test covers all three model-facing schemas** (work report, plan, review), not only
   the work report, and asserts exit 0 plus `runStructured`-equivalent validation of the last
   message.
4. **Fallback, not default:** keep an adapter option `outputSchema: "strict" | "off"`. With `"off"`
   it omits `--output-schema` and relies on the prompt (which embeds the JSON Schema) plus SK-307's
   one repair. Use it only if a future CLI or provider version rejects even the transformed schema.
   Dropping `--output-schema` entirely is **not** recommended as the default: provider-enforced
   structure is the main protection against `invalid_output`, which costs a full invocation plus
   a repair (PRD §9.6).
5. **Update the spike report:** record B1 with the exact provider error, the transform, the real
   SIGINT pass, and re-state the Codex-vs-fallback decision only after the opt-in test passes for
   all three schemas on a real device.

### Optional-null normalization: duplicate of SK-307

The fix also adds `src/adapter/output-schema.ts` exporting `normalizeOptionalNulls(value,
originalSchema)` (≈ 110 lines + tests). **The adapter never calls it.** It is a free-standing
helper meant for the validation boundary. SK-307, which is in progress on
`task/SK-307-structured-output` and was told to do exactly this, already has its own
implementation in `structured.ts` (an "undo the provider's required-but-nullable placeholders using
the ORIGINAL schema" pass). So it is a **duplicate**, not a conflict: different files, no merge
conflict, and it does not change the raw-output contract. But two normalizers would drift.

**Owner: SK-307 (`src/adapter/structured.ts`).** Normalization is part of validation, and §9.1/§9.3
put validation and the single repair in the structured runner, never in the adapter. The adapter
owns only the provider-side transform (`toCodexOutputSchema`), and the two meet only through the
original `outputSchema`.

Required action before or at merge (no further fix round needed; the orchestrator or SK-307 can do
it mechanically):

1. Remove `normalizeOptionalNulls` and `src/adapter/output-schema.ts` from SK-207. Keep the
   `toCodexOutputSchema` tests (the transform section of `output-schema.test.ts` can move to
   `codex.test.ts`).
2. SK-307 adopts the useful round-trip cases from `output-schema.test.ts` (transform ⇒
   provider-shaped value with nulls ⇒ `structured.ts` normalization ⇒ original Zod `parse` for
   Plan, WorkReport and Review; required nulls and unknown keys still rejected) as tests of its
   own normalizer.
3. The spike report's "B1" section should point at `structured.ts` as the normalization owner.
