## Verdict: **PASS_WITH_NOTES**

The write loop follows ARCHITECTURE §7.2 closely:

* fetch → `reset --hard origin/main` → replay → seen-id check → intent → finalize → plumbing commit
  with a single parent → `update-ref` with the expected old value → plain push → observe outcome.
* The event id is fixed before the loop. Retries back off through the injected `Clock` and `rng`.
  `publish` calls are serialized FIFO, and a failing intent cannot poison the queue.
* Lost acknowledgements are resolved through `seen_event_ids`, plus the landed SHA for
  `unauthorized`/invalid outcomes that D3 does not mark seen. This is a careful, correct detail.

The integration tests run real `git`/`ssh-keygen` against local bare remotes. They cover the
8-way race, lost ack, a failed fetch after a successful push, a failed `add`, dropped and rejected
intents, D3, human-signer override, attempt exhaustion, size caps, and a recording runner that
proves no `pull`/`merge`/`rebase`/`--force` is ever issued. The notes do not block merge; note 1
must be addressed before SK-504/SK-505 rely on crash recovery.

## Findings

### Blocking

None.

### Non-blocking

1. **There is no way to re-publish with a known `event_id` after a process restart.** `publish()`
   always draws a fresh id. ARCHITECTURE §7.2 step 9 says "attempt journal keeps the intent for
   retry after recovery", and §11.4 reconciliation needs the *same* id so a publication whose push
   landed before a crash dedupes through `seen_event_ids` instead of being appended twice (for
   example a second `work.delivered` attempt). Add `opts.eventId?: EventId` (persisted in the
   journal before the first attempt) **before SK-504/SK-505**. Owner: SK-403 or SK-504, or a small
   architect follow-up to `publisher.ts`.
2. **Non-`GitError` failures fail closed immediately**, including a failure while observing *after*
   a successful push (for example a `readLog` error). The event may then have landed while the
   caller sees `failed`. Note 1 makes this recoverable (re-publish with the same id ⇒ seen).
   Without it, document the behaviour in the `PublishResult` doc comment.
3. A non-fast-forward push also waits a jittered backoff before re-observing. §7.2 says "go to 1".
   Backing off under contention is reasonable (it avoids a thundering herd in the 8-way race), but
   the first retry after a non-ff could be immediate to cut latency. This is optional.
4. `fullReplaySource` re-reads and replays the whole log on every observation (O(n) per attempt).
   That is acceptable as the SK-301 baseline; SK-302's incremental `Sync` must replace it in the
   daemon (SK-601 wiring).
5. `genesis.ts` writes `skep.json` with `JSON.stringify(…, null, 2)`, which matches the event
   serialization style. A round-trip test that `genesisState()` accepts the created root exists
   only indirectly through replay in the race tests; an explicit assertion in `genesis.test.ts`
   would make it obvious.
6. Fixture consistency: use `example.invalid` instead of `example.com` in
   `publisher-race.test.ts` `humanTask()`, to match the rest of the repo.

## Follow-ups

* Add `opts.eventId` to `Publisher.publish` and journal it (note 1), before SK-504/SK-505.
* SK-302: implement `StateSource` incrementally and keep the `state.tip === tip` contract checked
  in `observe()`.
* SK-601: wire `hints.publish({kind: "tip"})` after an `accepted` result (D18), not inside the
