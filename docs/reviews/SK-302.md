## Verdict: **FAIL**

The poller is otherwise well built:

* Incremental replay from the cached `{sha, seq}` with `LogReadError` ⇒ alarm + full replay.
* An `ls-remote` short-circuit that compares `main` **and** `hb/*`, and caches the *fetched* refs
  rather than the advertisement.
* `observeNow()` always fetches; HEAD is never reset (that stays with the publisher).
* Clock-driven adaptive interval with seeded jitter. Untrusted hints are rate-limited (≤ 1 extra
  cycle per 2 s), coalesced during a running cycle, and their SHA is never followed.
* Idempotent start/stop, a serialized observation queue that a failure cannot poison, invalid
  commits counted and alarmed once.

The real-repo tests prove incremental == full replay for accepted, rejected, invalid and duplicate
commits.

**One real bug blocks it (B1): when `Sync` is used as the publisher's `StateSource` (its stated
purpose), a normal race with the poller raises a false "history rewritten" alarm** and briefly
regresses the cache. The fix is small.

## Findings

### Blocking

**B1. A requested tip that is *older* than the cached state is treated as a history rewrite.**
`readState(tip)` always tries `readLog(from: cachedTip, ref: tip)`. If `tip` is an ancestor of the
cached tip, `readLog` throws `LogReadError`, and Sync emits `{ kind: "log_read" }` (the
"history was rewritten" alarm from SK-203) and full-replays, replacing the cache with the *older*
state. The test "alarms and fully rebuilds after remote history rewrites and rollback to genesis"
shows that any older requested tip takes this path.

That is correct when the **remote** `main` moved backwards. It is wrong when the **publisher**
asks for an older tip, which happens in normal operation with one shared clone:

1. The publisher's `observe()` fetches and resets to `origin/main` = X.
2. A poll cycle that is already running fetches Y (a newer remote commit) and caches it.
3. The publisher's `replayTo(X)`, queued behind it, finds the cache at Y ⇒ false `log_read` alarm
   + full replay + cache regressed to X. The publisher's push then fails non-ff and retries
   (functionally fine), but the human sees a history-rewrite alarm, which is a security signal.

**Required fix:**

* In the `replayTo` path, if `tip` is a known earlier position of the cached log
  (`tip === cached.genesis_sha` or `cached.outcomes.some(o => o.sha === tip)`), compute the state
  for `tip` (full replay to `tip`, or a small bounded cache of recent tips) **without** an alarm
  and **without** replacing `this.state`.
* Keep the alarm for the poller path, where the *fetched* remote `main` is behind or diverged from
  the cache (a real rollback or rewrite).
* Add a test: `replayTo(Y)` then `replayTo(X)` with X an ancestor ⇒ the state at X is returned,
  no alarm, and `current().tip` is still Y. The existing rollback test (via `observe`) must still
  alarm.

### Non-blocking

1. **Shared clone, unserialized git operations.** Sync's `fetch` runs in Sync's own queue, while
   the publisher's fetch/reset/add/commit/update-ref run outside it on the same directory.
   Concurrent `git fetch` calls can collide on ref locks ("cannot lock ref"). Both sides retry
   (publisher: `GitError` ⇒ backoff; Sync: `sync_failed` alarm, next cycle), so this is safe, but
   it is noisy. SK-601 should run both through one clone-level mutex, or the publisher should take
   Sync's queue for its fetch/reset phase. Record it in SK-601's brief.
2. **Listener exceptions propagate.** `readState` calls `onState` listeners synchronously, so a
   throwing listener fails the observation (and a publisher `replayTo`). Wrap each callback and
   turn failures into an alarm.
3. `fetchedAtMonoMs` is also refreshed by an unchanged `ls-remote` (documented). That is the right
   meaning ("last successful remote observation"). `skep status` should label it "checked"
   rather than "fetched".

## Implementer contract note: device identity and active polling

The brief's `Sync` constructor has no device or agent identity, so the implementation treats
**any non-terminal task** as active (20 s ±25 %) instead of "an active **local** task" (§11.1).

**Decision: acceptable for the MVP, no fix in SK-302.** Correctness never depends on the poll
interval (hints and polling are availability-only, §17.2). The cost is bounded: an unchanged cycle
is one `ls-remote` thanks to the short-circuit, so with a handful of devices this is a few cheap
requests per minute. A task waiting on the human (`awaiting_approval`, `escalated`) would keep
every device at the active rate for hours, which is wasteful but harmless.

Follow-up for SK-601: add an optional `isActive?: (state: State) => boolean` dependency
(default = current behaviour). The daemon passes "a task in `executing`/`interrupting`/
`reviewing`/`replanning`/`planning` with an item assigned to, a lease held by, a review pending
from, or ownership by one of my slots". This is a constructor-option addition, not a contract
break, and the measurement in SK-609 decides whether it matters.
