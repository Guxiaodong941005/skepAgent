## Findings

### Blocking

None.

### Non-blocking

1. **`topic` is only `string(1..1024)`.** §17.3 defines it as 26 base32 characters
   (`base32(sha256(...))[0..26]`). Tightening it to `/^[a-z2-7]{26}$/` would stop a hint from
   carrying arbitrary text through the topic field (a free-form side channel, even if untrusted
   and harmless to state). Do this in SK-701 (relay) when the topic derivation is implemented, or
   in a one-line follow-up here before SK-302 depends on it.
2. `FakeHintChannel.publish` silently discards publications made before `start()`. That is
   consistent with "never rejects", but a publisher test that forgets to start the channel would
   see an empty `published` list. Add a doc comment, or record regardless of the subscription
   state.
3. `FakeHintChannel` ships in `src/` (it is emitted to `dist/`), as the brief allowed. A
   `@internal` / "test helper" JSDoc tag would make that intent clear to future readers.
4. The size check uses Node's `Buffer`. If hints ever need to be validated in a non-Node relay
   runtime (SK-701 worker), `new TextEncoder().encode(json).length` is the portable equivalent.

## Follow-ups

* SK-302 is now unblocked on the transport side (it is still gated on SK-301). It should use
  `FakeHintChannel.emit` for the rate-limit and forged-hint criteria.
* SK-701 (relay): enforce the topic format (note 1) and reuse `HintSchema` on both ends,
  rejecting invalid frames before fan-out.
