## Verdict: **FAIL**

`AttemptRunner` is a thorough implementation of the §9.7 pipeline:

* Journaled, resumable steps from `claimed` to `delivered_published`. The adapter launch identity
  (pid, pgid, start token) is fsynced through a runtime factory before the invocation continues.
* One fix-up with redacted check-log excerpts and a read-only diff; the work prompt says the agent
  has no usable git (G13). The mirror is fetched before trusted checks and the secret scan (G14).
* Daemon-signed commits with hooks and global config disabled and a filtered daemon git env.
* Code first, then record: pushes are verified via the remote ref, and a fresh reverify happens
  before the PR and again before `work.delivered`.
* The publish `eventId` is fsynced (`publish_pending`) before the first attempt and reused on
  recovery (F17). The interrupt ladder is bounded by `shutdownMs`, falling back to
  `invocation_state: unknown` (F18). Unknown invocations are never re-run.
* Secret pipeline: pattern scan, gitleaks via SK-502's hardened `scanSecrets`, model output
  (including JSON-escaped secrets), journal and streamed adapter capture are all redacted or
  checked (G7).
* Checkpoints for barriers with a signed WIP commit pushed before the event, and a mechanical
  snapshot.

**One protocol bug blocks it (B1): a secret hit publishes nothing at all, so the lease is never
ended on the blackboard.**

## Implementer notes: judgement

* **The runtime factory journals launch identity.** **Accepted.** Binding the adapter to a
  wrapping `RuntimeBackend` that fsyncs `invoked{pid,pgid,start_token}` before returning the
  handle is exactly what SK-505 needs (§11.4). Direct adapters are limited to process-free fakes.
* **Secret hits fail locally without publication.** **Rejected: B1 below.**
* **Recovery of an interrupted barrier with an unknown invocation outcome ⇒
  `checkpoint.recorded{invocation_state: unknown}`; daemon git env filtered.** **Accepted.** This
  matches PRD §10.6 ("never re-run an invocation whose outcome is unknown ⇒ `work.failed{crash}`
  or `checkpoint.recorded{unknown}`") and §11.4.

## Findings

### Blocking

**B1. A secret hit leaves the lease held on the blackboard.** `secretFailure()` records a local
`failed{secret_detected}` and returns. No event is published, by design (and tested). The holder's
lease therefore stays `leased` with no end event:

* the task stays `executing` with that item blocked;
* no retry or escalation happens (`work.failed` would let the reducer apply the item-retry budget
  or escalate, §5.5);
* the human is not told through the blackboard; `skep status` only shows a lease that later looks
  stale, and needs a manual revoke.

The failure class `secret_detected` was added to `work.failed` (D11) precisely so this outcome
can be recorded. "Nothing published" in the brief means **no code, PR, commit text or other
content**, not "no event".

**Required fix:**

* On a hit, publish `work.failed{class: "secret_detected", detail: <fixed text such as "Secret
  scan blocked publication; see the local journal">}` through the normal
  `preparePublication`/`publish` path (persisted `eventId`, fenced intent).
* Do not run the publication-time scan on the code range for this event (it would loop). Check
  only that the event JSON itself passes `findSecrets`, which a fixed detail guarantees.
* Still push no code, open no PR and include no model text.
* Apply the same rule to the checkpoint path: when a barrier checkpoint hits a secret, publish
  `work.failed{secret_detected}` (allowed in `interrupting`, where it settles the barrier) instead
  of leaving the barrier waiting for its deadline.
* Update the `it.each(["pattern","gitleaks","model"])` test: `publish` is called once with a
  `work.failed` whose detail contains no secret; no remote branch; no PR.

### Non-blocking

1. `scan()` runs again after `push()` with identical inputs. That is harmless but redundant,
   because the pre-push scan already gates the push. Keep it only if it is meant to cover a
   concurrent mirror update, and say so in a comment.
2. Each invocation writes `invoked` twice: once from the capture wrapper (pid `null`) and once
   from the runtime factory (pid set). Recovery treats either as "outcome unknown", which is
   conservative and correct. SK-505 should key adoption on the last record that has a pid.
3. `attempt.ts` is ~1,000 lines. Splitting publication/recovery and secret handling into
   separate modules would ease SK-505/SK-601 reviews. This is optional.
