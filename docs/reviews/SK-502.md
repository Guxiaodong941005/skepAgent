## Findings

### Blocking

**B1. The agent can disable the secret scan.** `scanSecrets` runs `gitleaks git … .` with the
**agent's worktree** as the scan source and without `--config`. In gitleaks v8, the configuration
precedence when no `--config`/`GITLEAKS_CONFIG` is given is the **`.gitleaks.toml` in the scanned
source directory**. gitleaks also reads a `.gitleaksignore` (finding fingerprints) from the source
by default, and honours inline `gitleaks:allow` comments. All three live in content the agent
writes and the daemon commits into the scanned range. An agent (or a prompt-injected model) can
therefore add a `.gitleaks.toml` with a catch-all allowlist, a `.gitleaksignore`, or
`// gitleaks:allow` next to a leaked key, and the delivery passes the scan.

That violates the same trust rule §9.6 applies to checks: trusted configuration must come from
`base_commit`, never from the worktree. It also weakens PRD §9.6 step 7 / §11.5 and the
defence-in-depth role assigned to gitleaks in §16 / D19. The stubbed tests cannot catch it.

**Required fix:**

1. Always pass `--config <daemon-owned file>`:
   * the repository's `.gitleaks.toml` read via `git show <base_commit>:.gitleaks.toml` from the
     **mirror**, written to a daemon-owned temp file; or
   * if absent, a minimal `[extend] useDefault = true` file.

   Also set `GITLEAKS_CONFIG`/`GITLEAKS_CONFIG_TOML` to nothing in the env.
2. Pass `--gitleaks-ignore-path <daemon-owned path>`, either an empty file or the base-commit
   `.gitleaksignore`, so the worktree's ignore file is never read.
3. Pass `--ignore-gitleaks-allow`, so inline allow comments added by the agent do not suppress
   findings. Legitimate exceptions go into the base-commit config, reviewed by the human.
4. Tests:
   * stub-level argv assertions for 1–3;
   * an opt-in real-gitleaks test (skipped if the binary is absent): a commit range that adds both
     a catch-all `.gitleaks.toml` and a fake key ⇒ `secrets_detected`.

### Non-blocking

1. **Exit code mapping (implementer's contract note).** `CheckRun.exit` is an integer: a timeout
   ⇒ `124` (the `timeout(1)` convention) and any other signal-only exit ⇒ `1`. **Judgement:
   acceptable.** It fails closed, because `exit ≠ 0` is a failure, and the journal keeps
   `timed_out` and `signal` for diagnosis. Two refinements: (a) map signal exits to `128 + signo`
   (e.g. SIGKILL ⇒ 137, the shell convention) instead of `1`, so evidence readers can tell a crash
   from an ordinary failure; (b) note that a check that itself exits 124 is indistinguishable in
   `CheckRun` and only disambiguated in the journal.
2. **Check logs are not redacted.** The runtime writes the raw log (0600, local), and its digest is
   evidence. Keep the raw log local and unredacted so digests stay verifiable, but SK-504 must
   redact any log excerpt it publishes or prompts with (SK-506 streams), e.g. in the fix-up
   prompt.
3. `load()` assumes `baseCommit` is already in the mirror. Callers (SK-504) must `mirror.fetch()`
   first; the error message ("merge a valid checks file") is misleading when the commit is simply
   not fetched. Distinguish "unknown commit" from "missing file".
4. The credential-name denylist for trusted build variables (`*_KEY`, `*_TOKEN`, `AUTH`, …) also
   strips harmless names such as `CACHE_KEY`. That is acceptable and conservative; document it in
   the checks-file docs (SK-608 runbook).
