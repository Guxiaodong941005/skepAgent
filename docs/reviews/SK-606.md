## Verdict: **PASS_WITH_NOTES**

`createDeliveryDuty` fills SK-601's stub with the full §9.8 / D14 / D15 owner flow.

* **When it runs:** when the task is `delivered` ∧ `verified == null` and this slot is the owner,
  keyed by `owner_gen + plan_hash + activation seq`. A `resume_with_plan` (D15) therefore triggers
  a fresh verification even though the hash is the same.
* **Verification:**
  * a private worktree at the **top-of-stack delivered SHA**;
  * the **union of every item's acceptance checks**, including carried-over merged items, run
    once through SK-502's trusted `ChecksRunner` (checks only from `base_commit`, run as the agent
    user with `agentEnv`, D19);
  * every `CheckRun` must name the delivered SHA and the expected check;
  * `passed` requires exit 0 **and** zero parsed failures;
  * the payload is scanned with `findSecrets`.
* **Publication:** one `task.verified{passed}` through a fenced intent that re-checks owner, plan,
  activation and head; **never `work.failed`, and no automatic re-run**. On failure the human is
  notified once, and again after a notification error, without re-running checks.
* **Merges and stale PRs:**
  * `prState` per delivered item ⇒ `item.merged` with the **actual merge SHA**;
  * the next PR is retargeted to the base once its predecessor is merged, repaired idempotently
    after a crash;
  * PRs from stale epochs and removed items are closed, while carried-over (D7) deliveries and live
    leases are preserved;
  * on cancellation every attempt PR is closed.

The `stacked-delivery` scenario proves the brief end to end. W2 starts from W1's delivered SHA with
its PR based on W1's branch; a failing combined check gives `escalated(verification_failed)`;
`skep decide --resume` (the same intent spec) returns the task to `delivered` with `verified ==
null`; re-verification passes; the human merges; W2's PR is retargeted to `main`; the task is
`done`. The same seed gives the same tip.

## Findings

### Blocking

None.

### Non-blocking

1. **Verification checks are journaled into the top item's finished attempt.** `ChecksRunner.run`
   appends `check_started`/`check_run`/`checks` to `<task>/<top>-e<epoch>.jsonl`, whose last step
   was the terminal `delivered_published`. After that, `Journal.unfinishedAttempts()` lists the
   attempt again. On the next restart SK-505's reconciler kills any recorded verification process
   group (good), then finds no matching lease and appends `stale` to a delivered attempt. That is
   misleading in the journal and in `skep status` diagnostics. **Fix:** give verification its own
   journal key, e.g. a pseudo-attempt per task + activation (needs a journal path that accepts it),
   or append a terminal `verification_done` step that `TERMINAL_STEPS` recognises. Do it before
   SK-609.
2. **Code-host call volume.** Every owner and assignee tick calls `prState` for every delivered
   item and `findPr` for **every** past epoch of every item (`closeStale`), indefinitely, with the
   tick at 20 s while active. With `gh` against GitHub that is a steady API load and can hit rate
   limits on a long task. Cache terminal PR states (merged/closed) and the "no stale PR for epoch
   e" result per `(task, item, epoch)`, or run `closeStale` only when the epochs change.
3. `observeMerges` retargets to `record.plan.base.branch`, whereas SK-601's attempt inputs use
   `task.base_branch` for a merged predecessor. They are equal by construction (the plan's base is
   validated against the task), but using one source would avoid drift.
4. Register `stacked-delivery` in `scenarios/index.ts` (SK-605 or the orchestrator).
