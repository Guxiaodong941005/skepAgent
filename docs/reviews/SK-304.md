Most of the work is good. Invariants 2, 3, 4, 8 and 9 are implemented as stated, read the
reducer's own state and helpers instead of re-deriving handler rules (`activeLeaseCount`, barrier
`closed_seq`), and share one incremental replay. The seeded generator builds only events that the
current state permits and adds forged entries. The 1,000-log property test (full == incremental,
invariants, forged no-ops) runs in about 28 s.

**Invariant 6, however, reports a violation for a legal log** (B1, reproduced below). `skep doctor`
and the SK-401 simulator would raise false alarms on a reachable state. The generator never
produces review-round escalations, so the property test cannot catch it (B2). The root cause is
partly the old spec wording of invariant 6, which this review corrects (architect decision D20,
below). The fix in the code is small.

## Findings

### Blocking

**B1. Invariant 6 is a false positive on legal logs.** `checkBudgets` requires `review_rounds ≤
budget` for every non-escalated, non-terminal task. A review-round escalation followed by
`resume_with_plan` is legal and leaves `review_rounds` above budget while `executing`. The
`replan_count` side has the mirror problem in a weaker form: the blanket "ever resumed" exemption
hides real violations.

**Required fix: check invariant 6 per transition (D20), using the existing `steps`.** For each
accepted step on task `t`:

* If `after.replan_count > before.replan_count` and `after.replan_count > budgets.replans`, then
  `after.barrier.escalate` must be `true` (code `replan_budget`).
* If `before.barrier?.escalate === true`, the status may not become `replanning` (it may only stay
  `interrupting` or become `escalated`; code `replan_budget_settle`).
* If `after.review_rounds > before.review_rounds` and `after.review_rounds >
  budgets.review_rounds`, then `after.status` must be `escalated` (code `review_budget`).

Remove `resumedTasks` and the state-based check.

**B2. The generator cannot reach review-round escalations.** `review.submitted` is always emitted
with `blockers: []`, and the generator has no path to repeated `plan.rejected` or blocked
proposals. As a result, B1 slipped through. Add `block` reviews (with typed evidence, as the
schema requires), `plan.rejected`, and a `resume_with_plan` after a review-round escalation to the
candidate set. Extend the coverage test to require at least one review-round escalation and one
over-budget `resume_with_plan`.

**Also add a regression test:** the repro log above, built with `LogBuilder`, must yield
`checkInvariants(...) == []`. A mutated variant, where the third rejection does *not* escalate
(constructed state), must yield `review_budget`.

### Non-blocking

1. Invariant 3 checks `seen_event_ids` only for `rejected` outcomes. Asserting that `invalid` and
   `duplicate` entries leave `seen_event_ids` unchanged too would make it complete.
2. `acceptedEvents` re-runs `checkStructure` on accepted entries. That is fine, but `walk` already
   replays everything, so the accepted events could be taken from the same pass to halve the work
   for `skep doctor`.
3. The generator's `REPO` uses `example.com`; switch to `example.invalid` for consistency.

## Architect decision on the implementer's question (invariant 6)

The implementer's reading is **correct in substance**. `replan_count` is a lifetime counter that
can remain above budget after `human.decided` (D12), and an over-budget barrier legitimately stays
`interrupting` until its leases settle (§5.5). The **spec text was wrong**. It is now recorded as
**D20** and fixed (uncommitted) in:

* `docs/ARCHITECTURE.md` §13.2 invariant 6, now per-transition, and §15 row D20.
* `docs/DEV-PLAN.md` SK-304 row and brief, which point to the D20 form.

The implementation still fails, because (a) it applied the allowance only to `replan_count`, not
to `review_rounds`, and (b) a blanket "ever resumed" exemption is not the same as the
per-transition rule.

### Remaining non-blocking notes

1. **Caller state overrides the last step.** `checkBudgets` uses the caller's `state` instead of the
   replayed `after` for the final entry (`entry.seq === state.seq ? state : point.after`). This is
   how the mutated regression test injects a broken transition. It is harmless for `skep doctor`,
   which passes the replayed state, but it makes invariant 6 the only predicate that trusts the
   caller over the replay. A doc comment on `checkInvariants` saying "the final `state` is assumed
   to equal `replay(entries)`, except in tests" would make that explicit.
2. `replan_budget` and `replan_budget_settle` have no negative test (only `review_budget` does).
   Constructed-state variants analogous to the review case (an over-budget replan with
   `escalate: false`, and an escalate barrier settling into `replanning`) would pin both codes.
3. The property suite now takes ~35 s for 1,000 logs of up to 40 events. That is acceptable;
   `SKEP_PROPERTY_LOGS` lets CI or local runs scale it.
