## Implementer decision: the replan fixture is a team task

D13 makes a solo plan hold exactly one item. The replan fixture must show a delivered item
carried over (D7) **next to** a replaced item that is re-leased at a higher epoch, which needs at
least two items. **Judgement: correct.** The alternative, a solo task upgraded by a team plan, is
also legal, but it would pin the D13 upgrade at the same time and mix two concerns in one hash. A
team task keeps the fixture about replanning only.

## Scope check

Changed: `test/fixtures/golden/*.json`, `test/integration/golden.test.ts`, `test/helpers/golden.ts`,
**plus `test/helpers/golden-scenarios.ts`**. The last file is not in the schedule's owned list. It
is a new SK-305-only helper (the scenario scripts that build the fixtures), conflicts with nothing,
and is the right place for that code, so it is accepted. No reducer, schema, `log-builder.ts` or
`random-log.ts` edits (SK-304's generator is not modified). **OK.**

Determinism: event ids and commit shas are derived from the scenario name and seq, so the scripts
always produce identical logs. The scripts read reducer state for preconditions and throw if a step
is rejected, rather than re-implementing handler rules.

Public-repo hygiene and D19: fixtures and helpers use only placeholders
(`git@example.invalid:example/app.git`, `https://example.com/example/app/pull/<n>`), the builder's
agent IDs and fixed timestamps. There are no emails, IPs, real hosts, keys, signatures or host
paths. Signatures are represented as `SignatureCheck` records, not key material.

## Findings

### Blocking

None.

### Non-blocking

1. **Placeholder consistency.** PR URLs use `example.com` (reserved by RFC 2606, acceptable). The
   rest of the repo standardizes on `example.invalid`. Switch when the fixtures are next
   regenerated. Because URLs are part of the hashed state, this is a deliberate
   `SKEP_UPDATE_GOLDEN=1` run.
2. **Add the D20 review-round-resume log.** The SK-304 review suggested pinning the B1 repro (a
   review-round escalation ⇒ `resume_with_plan` ⇒ `executing` with `review_rounds` over budget) as
   a golden fixture, since it is exactly the kind of legal-but-surprising state a future reducer
   change could break. Add it as a seventh fixture (`review-resume`), and extend `EXPECTED`.
3. The update path rewrites fixtures during test **collection** (`describe.each` body). That is fine
   for a manual command, but a parallel or watch-mode run with the env var set could write
   repeatedly. A guard that refuses `SKEP_UPDATE_GOLDEN=1` together with `--watch` (or doing the
   rewrite in a `beforeAll`) would be tidier.
4. "is the log the scenario script builds" ties each fixture to the current script. That is useful,
   but it means a scenario-script refactor fails the test even when the reducer did not change.
   The header says so ("a hash that moved without a reducer change means a scenario script
   changed"). Keep it, as it makes accidental edits to fixtures visible.
