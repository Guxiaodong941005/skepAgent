## Verdict: **PASS_WITH_NOTES**

All three required follow-ups and both optional ones are implemented and tested.

* **H1 (empty-token process-group kill).** `ProcessSchema` gains an optional `boot_id`, and
  `ReconcileProcesses.bootId()` reads the OS boot identity (`/proc/sys/kernel/random/boot_id` on
  Linux, `sysctl -n kern.bootsessionuuid` on macOS, via `execFile`, both checked to be UUIDs).
  An empty-token group is killed **only** when the journaled boot id equals the current one and
  the group's leader metadata is readable. Otherwise `process_unverified{boot_changed |
  missing_boot_identity}` is journaled and nothing is signalled.
* **H14 (verification journal).** Verification has its own journal key,
  `verificationKey(task, activation)` = `verification-<sha256(activation)>`, epoch 1, accepted by
  `assertKey` and `FILE_RE` under a strict regex.
  * A finished batch (last step `checks`) is not "unfinished", so the delivered item attempt stays
    terminal.
  * An in-flight verification remains discoverable, so a restart stops its process groups and
    then marks it `stale` without touching the item attempt.
* **H15 (code-host load).**
  * Terminal PR observations (merged/closed) are cached per `(task, item, epoch)`.
  * A completed retarget is remembered.
  * Stale epochs whose PR is absent or already closed are remembered.
  * `closeStale` runs only when `staleEpochsKey` changes: epochs **or** the preserved
    lease/delivery branches, which covers cancellation and release without a new epoch.
  * Failed observations are not cached.
* **H2 (pending delivery under a barrier).** A pending `work.delivered` for an interrupted attempt
  is replaced by a durable unknown-outcome checkpoint. It is journaled as a new `publish_pending`
  before publishing (F17), so the barrier settles instead of waiting for the deadline.
* **H3 (PR merged/closed before `work.delivered`).** The reconciler publishes a fenced
  `work.failed{crash}` with "PR was merged/closed before work.delivered; inspect the PR before
  retrying", so the lease no longer stays held.

**Main note:** no journal writer records `boot_id` yet. Process records are written by
`src/exec/attempt.ts` and `src/exec/checks.ts`, which this task did not own. In production an
empty-token group is therefore **never** killed now. That is the safe direction (no unrelated
group can be signalled after a reboot), but orphans from a leader whose start token was
unreadable will survive a restart (note 1).

## Findings

### Blocking

None. Every criterion is met in the owned files, and H1's guard fails safe.

### Non-blocking

1. **Record `boot_id` when a process is journaled.** `attempt.ts` (invocation `process` record)
   and `checks.ts` (check `process` record) should add `boot_id:
   await processes.bootId()`, reusing `nativeReconcileProcesses.bootId`. Until then, F19's
   "kill orphan children of a dead leader" never happens for empty-token records. That is small
   (two call sites plus tests). Do it before or during SK-609 (SK-504/SK-502 area, codex), or
   accept and record it in the run report if empty tokens never occur on the run devices (check
   the journals).
2. **A closed PR is cached for the daemon's lifetime.** If a human closes a delivered PR by
   mistake and then reopens and merges it, `observeMerges` keeps the cached `closed` state and
   never records `item.merged` until `skepd` restarts. Cache only `merged` permanently, or let
   `closed` expire (e.g. re-poll every N ticks).
3. The in-memory caches (`terminalPrs`, `settledEpochs`, `staleScans`, `retargeted`) are
   rebuilt after a restart. That is intended: the first tick after a restart rescans once.
