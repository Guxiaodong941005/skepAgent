## Findings

### Blocking

None.

### Non-blocking

1. **"Sorted keys" relies on the serializer.** The DEV-PLAN row says "stable JSON, sorted keys".
   `statusView` returns objects whose key order is fixed by construction, and the test serializes
   with `canonicalJson`, which sorts keys. That is fine, but SK-604 (`--machine` output) must print
   via `canonicalJson`, not `JSON.stringify`, to keep the guarantee. Add that as a one-line note in
   SK-604's brief.
2. The assertion `canonicalJson(view) === JSON.stringify(JSON.parse(canonicalJson(view)))` holds
   for any canonical output, so it adds little. The meaningful checks are the replay comparison
   and the reversed-insertion-order comparison next to it.
3. Two slightly different "parked" definitions: `leasesHeldBy.parked` = item `interrupted`, while
   `StatusItem.parked` = item `interrupted` ∧ lease present. They agree for every state the
   reducer can produce (an `interrupted` item always keeps its lease until activation, D16). A
   shared one-line helper would remove the doubt.
4. `claimableItems` returns all ready items even when only `max_parallel − active` of them could be
   claimed (for example, two ready items with one free slot). The second claim is then rejected
   with `max_parallel`, which the publisher handles (intent re-derivation, §6.1). Worth a doc
   comment so SK-403/SK-601 do not enqueue more claims than free slots.
5. `barrierStatus` uses an `as TaskState` cast after a null check that could instead bind
   `const task = state.tasks[taskId]` once. This is cosmetic.

## Follow-ups

* SK-604: serialize `statusView` with `canonicalJson` (note 1).
* SK-403 / SK-601: claim at most `max_parallel_items − activeLeaseCount` candidates per tick
  (note 4).
* After SK-202 merges, add one log-driven (not constructed) barrier case to `views.test.ts` (it can
  be folded into SK-304's property tests).
